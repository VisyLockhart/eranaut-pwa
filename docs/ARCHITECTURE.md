# 架構與設計決策

[English](ARCHITECTURE.en.md) · **繁體中文**

這份文件記錄「為什麼做成這樣」,不是「怎麼跑起來」(那部分請看 [`README.md`](../README.md))。目的是留下決策脈絡:試過或考慮過哪些做法、為什麼放棄、換來什麼取捨。程式碼註解裡的 `D-xx` / `R-xx` 編號說明見 [`DESIGN-NOTES.md`](DESIGN-NOTES.md)。

整體形狀先放在前面:

```
 瀏覽器 / 手機主畫面 (Angular PWA)
        │  同網域 /api/*(session cookie,無 CORS)
        ▼
   Caddy ──靜態檔── web/dist
        │
        ▼
 Fastify API ─┬─ 公開埠:網站用
              ├─ 內部埠:Discord bot 用(共用密鑰)
              ├─ SQLite(better-sqlite3,單一檔案)
              ├─ OCR(PP-OCRv4,同一個 process,只在記憶體)
              └─ 兩個排程:30 秒提醒輪詢、每日資格比對
        │
        ├─ Discord API(OAuth、查成員與身份組、DM / 頻道訊息)
        └─ Web Push 服務(FCM / Apple 等,VAPID)
```

## 1. 做成 PWA,而不是原生 App

最初的選項是 Flutter 做 Android + iOS 原生 App。放棄的原因很實際:開發成本高,還要處理上架審核與 Apple 開發者年費;而這個工具的使用情境是「看一眼倒數、偶爾更新」,網頁足夠。

**取捨**:PWA 在 iOS 上有限制——必須「加入主畫面」並從圖示開啟,才有 `PushManager` 可用。換來的是一份程式碼同時服務桌機與手機,也不需要任何商店。如果日後 iOS 推播限制讓太多人放棄用推播,才會回頭評估原生 App。

## 2. 資料只有一個入口:Discord bot 也走 API

配套的 Discord bot([`eranarch-bot`](https://github.com/VisyLockhart/eranarch-bot))需要查詢潛艇資料(例如 `/eran` 指令)。最直覺的做法是讓 bot 直接開同一個 SQLite 檔案,但這被否決了:`better-sqlite3` 是同步寫入,多個 process 同時寫一個檔案會出狀況,而且資料存取邏輯散在兩個地方,規則一變就會不一致。

因此所有資料存取都經過同一支 API。API 在同一個程序裡開**兩個埠**:

- **公開埠**:網站使用,走 session cookie。
- **內部埠**:只給 bot 使用,Bearer 共用密鑰驗證,不對外發佈、不經反向代理。密鑰比對先雜湊成等長再用固定時間比較,避免長度與內容的時間差。

兩個埠共用同一層 service / repository,差別只在「誰在呼叫」與「身份怎麼解析」。內部埠的每個請求還帶著呼叫者的 Discord ID 與身份組,API 用同一個判斷函式再檢查一次權限,不信任 bot 端自己篩過。

## 3. 資料庫選 SQLite

考慮過 Oracle Autonomous Database(設定太複雜)、Redis / Kubernetes(過度設計)。這個系統的規模是一個約 128 人的社群、單一主機,SQLite 單檔案加每日備份就夠了,維運成本最低。

幾個配套決定:

- **主鍵一律 UUID v4(TEXT)**,不用自動遞增整數。跨環境匯入或合併時不會撞號。
- **時間一律存 UTC 的 ISO 字串**,台北時間在 API / 前端層轉換。
- **提醒方式用位元旗標存在一個整數欄位**(DM、頻道 @、推播各一位)。考慮過「組合列舉」(1=全選、2=全不選⋯⋯):值會隨方式倍增,「全選」的語意會隨擴充漂移,可能在使用者不知情下開啟新方式。**對外 API 不暴露位元數字**,而是回具名布林,前端不依賴位元排列。
- **migration 只能新增、不可修改已發布的項目**。

**取捨**:SQLite 無法水平擴充,規模明顯超過預期時要重新評估(例如改 Postgres)。這是刻意接受的——不為不存在的規模付複雜度。

## 4. 認證:Discord OAuth + 伺服器端 session

登入流程是標準的 Authorization Code Grant,**換 token 在後端**(client secret 不能出現在前端)。後端只用 `identify` 範圍取得使用者 ID,然後用 bot token 查該使用者在指定公會的成員資料與身份組。Discord token 用完即丟,不入庫。

幾個值得說明的選擇:

| 選擇 | 否決的方案 | 原因 |
|---|---|---|
| 伺服器端 session cookie(DB 只存雜湊) | 自簽 JWT + refresh token | 只有單一 API 加 SQLite,無狀態驗證的優勢用不上;refresh 機制增加複雜度,而且 JWT 無法即時撤銷 |
| `SameSite=Lax` | `SameSite=Strict` | Strict 在跨站頂層導覽不帶 cookie:OAuth 回呼時 `state` cookie 帶不上,登入會失敗;使用者從 Discord 連結進站時首屏也會像未登入 |
| 前端與 API 同網域,不做 CORS | 跨來源部署加 `@fastify/cors` | 同網域根本不需要 CORS;開放跨來源只增加攻擊面 |
| 改資料的請求檢查 `Origin` | 另做 CSRF token | `SameSite=Lax` + 同網域 + Origin 檢查已涵蓋主要攻擊面;token 前後端都要維護,對這個規模是過度設計 |
| 只用 `state` 防偽造 | 加 PKCE | 後端持有 client secret,攔到授權碼的人換不到 token |
| session 閒置 30 天過期 | 加絕對上限 | 小社群優先方便;失去資格者已有每日比對刪除其 session |

另外,GET 端點一律不得有副作用,這是 `SameSite=Lax` 方案成立的前提。

## 5. 「誰有資格」只在一個地方定義

誰能使用,由 Discord 身份組決定。規則用一個字串表達:`,` 為「或」、`+` 為「且」,例如 `A+B,C` 代表 (A 且 B) 或 C。起初只支援「任一符合」,後來發現實際的管理方式可能要求同時擁有多個身份組,所以改成可組合。

規則只定義在 API 一處,網站登入、每日比對、bot 指令**共用同一個判斷函式**。否決了「bot 自己快取成員名單再篩」——那會複製一份規則,AND / OR 一變兩邊就不一致。

**失去資格時標記停用,不刪資料。** 離開伺服器或被移除身份組的人,資料保留,恢復資格後自動復原。手動停權者與自動停用者用同一個欄位區分,自動比對一律不動手動停權者。

**每日資格比對的防呆**:向 Discord 取不到成員名單、或名單為空時,整次放棄、不做任何變更——否則 Discord 暫時故障會把所有人誤停用。比對在啟動時先跑一次,服務停機後重啟也能立刻補上。

## 6. 截圖辨識:自架 OCR,不連外部服務

這是整個專案裡取捨最多的一塊。

**要解決的問題**:使用者要登記多艘潛水艇的返航時間,逐艘手動輸入太累。讓使用者上傳遊戲截圖,系統自動讀出每艘艇的名稱與剩餘時間,再由使用者核對。

**引擎的選擇**:

- 先試了 Tesseract:要辨識的內容以中文為主、遊戲小視窗可能有透明度,實測成功率很低。
- 外部服務(雲端視覺 API、多模態 LLM)也否決:不希望辨識還要再連去外部服務。
- 最後採用 **PP-OCRv4**(透過 `@gutenye/ocr-node` 與 `onnxruntime-node`),跑在 API 同一個 process 裡,免費、能處理繁體中文與半透明視窗。

**處理流程**:

1. 收到的圖片先依 EXIF 轉正,縮到長邊 1280 px(只縮不放)。實測縮到 1280 準確度不變,但手機大圖速度快 3 倍以上、記憶體小很多。
2. 轉成原始像素餵給引擎。**全程只在記憶體,不寫磁碟**——因此不需要圖片回收排程。
3. 引擎回傳文字行與各行信心值,交給**純函式的解析器**轉成潛艇資料。

**解析器是純函式**(不碰影像與模型),這讓它能用固定的 OCR 輸出做單元測試。它支援兩種截圖格式:「請選擇潛水艇」選單視窗,以及「飛空艇探索 / 潛水艇探索」情報頁。PP-OCRv4 有已知的誤認模式,解析器針對它們設計:

- 艇名前綴字形被認錯(潛→潘 / 潜 / 蜓⋯⋯):**位置看順序,不看名稱**,名稱前綴再校正成預設名稱。
- 數字之間被夾進空格、`-N` 與時間黏在一起:時間用「數字加單位」的樣式抽取,不依賴空白。
- 簡體字形(级 / 钟 / 时):先正規化。

**無法確定的就標為可疑,不猜。** 信心低於 0.85 的行,名稱與時間都會標示「請核對」,使用者在送出前必須看過。這個門檻是用 11 張真實截圖(29 艘艇,信心最低 0.869、中位數 0.93)與 77 張人工劣化的圖(203 艘全部讀對、沒有漏標)校正出來的。

**資源保護**:同時辨識的張數限制為 2,排隊上限 8,超過直接回 429 `busy` 並帶 `Retry-After`,不讓大量請求把記憶體吃光(每張排隊中的圖都還握著上傳的 buffer)。單一使用者同時也只能有一個辨識請求在進行。

**職責分離**:OCR 端點只辨識、不寫資料庫;建立與更新是另外的端點。辨識結果回到前端讓使用者核對,確認後才送出更新。

## 7. 時間以後端為準,並補償使用者的等待

前端**只送「剩餘時間」**,不送算好的返航時刻;返航時間 = 後端收到請求的時間 + 剩餘時間。時間權威在後端。

但使用者從截圖、核對到按下送出之間會花時間。前端為每一列記錄起算時間戳(而不是累加計數器,因為瀏覽器會降速或凍結背景分頁),畫面上的剩餘時間每滿一分鐘減一,**送出時不足一分鐘的零頭無條件進位多扣一分鐘**——寧可返航時間偏早、不偏晚,因為提早提醒的代價遠低於讓人錯過。任一列扣到 0 就視為資料作廢,要求重新辨識。

## 8. 提醒:資料庫加輪詢,不用外部佇列

提醒的需求是「返航前 N 分鐘通知」。設計成:

- 待發提醒存在 SQLite 一張表,API 進程內**每 30 秒輪詢**一次到期的項目,用 `@fastify/schedule` 防重疊執行,並隨 Fastify 的關閉流程收尾。
- 不用 Redis 或外部佇列,也不用記憶體計時器——待發提醒在資料庫,服務重啟後直接接續。
- **全系統只有兩個排程**:這個輪詢與每日資格比對。

**不累積資料**:提醒以「潛艇」(整批模式則是「工坊」)為鍵 upsert,每個鍵最多一筆。否決了「每次更新都新增並另設定期清理」——那會產生髒資料,還要多一支清理排程。

**發送與失敗處理**:

- 5xx 與網路錯誤每分鐘重試一次,總共最多 3 次;429 依 `retry_after` 等待,同樣算一次嘗試。
- 永久性錯誤(使用者關了私訊、封鎖 bot、已離開伺服器、頻道無權限)不重試,標記失敗並寫結構化 log。
- **私訊永久失敗時,不會自動改發頻道**:頻道訊息是公開的,所以不自動降級。
- 晚超過 30 分鐘的提醒視為「錯過」,不補發。
- 失敗只寫 log,不做使用者畫面。

## 9. 瀏覽器推播(Web Push)

推播是第三種提醒方式,和 Discord 私訊、頻道 @ 並存,使用者可複選。用標準 Web Push(VAPID 加 `web-push`),Angular 的 service worker 原生處理推播事件,所以關掉視窗甚至關掉分頁都收得到。

設計重點:

- **訂閱按裝置各自開關**:瀏覽器的授權與訂閱本來就是每台裝置獨立的。一位使用者可有多台裝置,一筆提醒會發給全部裝置;只要有一台成功就算已發送,重試時不會對已成功的裝置重複發。
- 推播服務回報訂閱已失效(404 / 410)時自動刪掉那筆訂閱;最後一台也失效時關閉推播位元。
- 登出與停用會清掉訂閱,避免登出後這台裝置還收到上一個帳號的通知。
- **VAPID 金鑰是選填的**:兩把都不設就整個停用推播(設定頁連這一項都不顯示),只設一把則啟動失敗。
- iPhone / iPad 的規則最特別:只有「加入主畫面並從圖示開啟」才有 `PushManager`,Safari 分頁裡完全沒有。所以前端先判斷平台,再判斷 API 是否存在,並在需要時引導安裝。

## 10. 前端

- **Angular**,元件使用 signals 與獨立元件。業務狀態放在「view model」服務(例如 `overview-vm`、`update-vm`),元件只負責畫面,因此大部分邏輯可以不碰 DOM 直接做單元測試。
- **PWA 的 service worker 只快取 app shell,API 一律走網路**。不快取資料,避免顯示過期的倒數。
- **總覽用單一 `GET /api/overview`**。否決了「列表端點內含潛艇」(工坊 CRUD 的回應型別會跟著變形)和「前端自己打 N 次再組合」(N 間工坊要 N 次請求,快照也要自己拼)。
- **個人偏好只存在該裝置的 `localStorage`**:工坊排序、介面大小、收合狀態。否決了存進資料庫——純個人偏好,不值得多一張表;手機與桌機排序不同是可接受的取捨。
- **介面大小用 CSS `zoom`**。副作用是 Safari 與 Chrome 對 `zoom` 下的 `vh` / `vw` / safe-area 處理不同,所以這類長度一律除以另一個變數校正。
- **本機開發自製轉發器**(`web/dev.mjs`):在 Windows 上 Vite 內建的 proxy 對 `/api` 會間歇出現 `ECONNRESET`,自製版對上游一律重用連線,並只對可安全重送的請求重試,實測沒有失敗。
- 純深色主題、斷點 768 px,手機與桌機是兩套總覽版面。

## 11. 部署:不開任何對外 port

```
Cloudflare Tunnel ──▶ Caddy(容器內純 HTTP)──▶ Fastify API
                         └─ 同時提供前端靜態檔
```

- 主機上**沒有開任何對外 port**;外部流量全部經過 Cloudflare Tunnel。TLS 由 Cloudflare 處理,Caddy 在容器內聽純 HTTP。
- 考慮過讓 Tunnel 依路徑分流到 API 與前端兩個容器、不經 Caddy,但前端仍需要一個靜態檔伺服器,省不掉,沒有比較簡單。所以由 Caddy 同時提供靜態檔與 `/api` 轉發。
- **快取標頭要小心**:帶雜湊檔名的 js / css 可長期快取;其餘(`index.html`、SPA 備援頁、`ngsw*.js`、manifest)一律 `no-cache`,否則 service worker 與新版本送不出去。
- 容器之間用 service 名稱互相呼叫,不用 `localhost`(不同容器不共享網路命名空間——本機測試正常、上 Docker 才打不通是常見的坑)。
- 想達成「不開 inbound」時,**不要**在 compose 網路加 `internal: true`:它會連 outbound 與 DNS 解析一併封鎖。只要不寫 `ports:` 就夠了。

## 12. 一個 monorepo

`shared/`(前後端共用的常數與型別)、`api/`、`web/` 放在同一個 repo(npm workspaces)。考慮過拆成 `eranaut-api` 與 `eranaut-web` 兩個 repo,但契約(固定清單、位元常數、API 型別)就要複製兩份或另發 npm 套件,對單人開發的規模太重,跨前後端的改動也要開兩個 PR。

## 13. 展示模式:讓真正的前端在沒有後端時跑起來

這個 repo 附有一個**建置時才啟用**的展示模式(`ng build --configuration demo`),部署在 GitHub Pages 供試玩:<https://demo.eranaut.aequoreranos.com/>。

**做法**:不改 `Api` 類別,而是在 Angular 的依賴注入裡換掉 `HttpBackend`,由一個假的後端(`DemoBackend`)攔截所有 `/api/*` 請求。所有畫面、`Auth`、各 view model 與 interceptor 完全不動,是同一份程式碼。假後端仿照真實 API 的驗證規則與錯誤格式(`validation_failed`、404、401),型別與常數取自 `shared`。資料存在瀏覽器的 `localStorage`,可隨時重設。

**用 `fileReplacements` 在建置時切換**:正式版的 `demo-providers.ts` 是一個空的 stub,`demo` 組態把它換成真正的假後端。因此**正式版的 bundle 不含任何展示程式碼**(建置後用 grep 驗證過)。

**為什麼不是把功能手動搬進早期的展示頁**:早期的 prototype([`eranaut-demo-page`](https://github.com/VisyLockhart/eranaut-demo-page),純 JavaScript 單檔)停在較舊的版本,看不到後來的推播、設定頁、介面大小、版面收合等功能。要手動重寫約 3000 行 Angular 的行為,還得長期維護兩份,等於把「展示頁落後」這個問題重做一遍。現在展示版和正式版共用同一份畫面,web 更新後重新建置就同步。

**推播在展示版**:沒有推播伺服器,所以不做真的推播。設定頁仍顯示推播開關,開啟只是取得通知權限,「傳送測試通知」改由本機 service worker 顯示——外觀與正式版一樣(包含 iPhone 主畫面 App 的系統橫幅),但不會排程提醒。

## 14. 航線模擬器

放在導覽的第 5 項,功能是把社群常用的網頁小工具(選航點算航行時間、配置搜尋、掉落反查)搬進來,並加上依目標的路線推薦。幾個取捨:

- **計算全是純函式**(`web/src/app/route/core/`):航點選取判斷(等級、距離上限、最多 5 點,每選一點就重算其他點能不能選)、最短順序、航行時間、配置搜尋(10⁴ 種配件組合)、路線推薦。不依賴 Angular,可以直接寫測試;公式用外部小工具已驗證的案例當基準,再由實際遊戲畫面的數字交叉確認。
- **資料集打包進程式碼,不進資料庫**:航點、物品、配件與等級表放在 `route/data/`,隨航線頁的 lazy chunk 載入,由 service worker 一起快取,所以離線也能用;更新資料靠重新部署。資料集是第三方資料的整理結果,**授權與 MIT 不同**(CC BY-NC-SA 3.0),獨立成帶 `NOTICE.md` 的資料夾。
- **「儲存配置」存資料庫、跨裝置同步**:每位使用者最多 10 組,存在 `route_subs`;一組配置可綁定多艘工坊潛艇(`route_sub_bindings`,一艘潛艇只綁一組,兩邊都 `ON DELETE CASCADE`,不需要清理排程)。只有「檢視狀態」(選到的海域與航點、臨時配置)留在各裝置的 `localStorage`。離線時顯示上次的清單快照、寫入需要網路,同一筆以最後寫入為準——這些取捨都刻意從簡。
- **「條件組合」把找路線的條件命名儲存**:每人最多 10 組,存在 `route_filters`,內容是一個 JSON 欄位 `spec`(必選 / 排除航點、海域、最長航行時間、想要的物品、排序)——這是整個資料庫第一個 JSON 欄位,因為它不會被查詢、整筆讀寫,拆成子表只會增加複雜度。**不存配置**:篩選條件是查詢、配置是參數,所以載入時不判斷「符不符合」,整組套用,衝突(等級不足、走不完)交給畫面上既有的即時提示說明;也不存「去過的航點」(那是裝置上的進度)。API 不認識航點與物品資料集(資料集在前端),只驗形狀與範圍,資料集已沒有的項目由前端載入時略過並提示。從列上選一組會整組套用、自動搜尋並收合海圖與條件區,讓結果直接出現。同步方式與儲存配置相同(進頁載入、回前景重抓、最後寫入為準、離線顯示快照)。
- **展示版關掉儲存、綁定與條件組合**:這些都需要登入與伺服器端資料表,展示版沒有。以注入權杖 `ROUTE_FEATURES` 控制(預設全開,展示組態把 `saving` 設為 `false`):畫面隱藏相關按鈕與「條件組合」列,`RouteVm`、`RouteFilterVm` 也不呼叫 `/api/route-subs`、`/api/route-filters`,配置與找路線的條件都只是畫面上的臨時狀態。同一個開關管三件事,是因為它們的理由相同(沒有伺服器),分開設旗標只會讓兩個 repo 更容易不一致。
- **不限制「做不到」的事,只提示**:例如超過重量上限只警告;燃料只顯示、不限制選取。模擬器的角色是幫玩家判斷,不是複製遊戲的所有限制。

## 已知限制與技術債

誠實列出目前沒做、或刻意不做的部分:

- **單一主機、單一 SQLite 檔案**,無法水平擴充。對目前的規模是刻意的選擇。
- **一個 API 服務一個公會**:資格判斷只認設定的那一個伺服器。
- **OCR 只針對繁體中文版客戶端的截圖校正**;其他語言版本的畫面沒有測試過。真實截圖樣本只有 11 張,雖然另有劣化圖補強,仍不代表所有裝置與縮放的情況。這些截圖不放在 repo(含玩家資訊),所以用真實引擎辨識真實截圖的整合測試(`ocr-real`)預設跳過,需指定 `OCR_TEST_DIR` 才會跑;一般測試跑的是解析器對固定 OCR 輸出的單元測試。
- **沒有端對端(E2E)測試**。後端有 API 層的整合測試(用 Node.js 內建的 `node:test`),前端是單元測試;瀏覽器層的行為靠手動與實機驗證。
- **這個 repo 不含部署檔**:`docker-compose.yml`、Tunnel 設定與備份腳本不在這裡,所以不是「clone 下來就能一鍵部署」的專案。
- **推播在 iOS 需要先加入主畫面**,這是平台限制,不是可以靠程式碼繞過的。
- 提醒訊息不附網站連結;私訊失敗不改發頻道(見第 8 節)。
- 航線資料集來自第三方,版本會更新;名稱部分由簡體轉繁體、尚未對照繁中服實機校正,等級上限與重量上限的部分數值是推定(清單見 `route/data/TODO.md`)。
- 展示版沒有的:真實登入、真實 OCR、真實推播排程;航線模擬的「儲存配置」、「綁定工坊潛艇」與「條件組合」(見第 14 節)。
